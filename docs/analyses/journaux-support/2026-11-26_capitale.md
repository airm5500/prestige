## Détail et correctifs proposés (non faits)

### J26-1 — « Enregistrer » sans les données de la vente

Fil d'Ariane du 25/11 :

- 12:24:48 : `GET vente/find/infosclienttpforupdating` ;
- 12:24:50 : « Enregistrer ».

`me.data` n'est rempli que dans le `success` de `loadVenteById` (`:1314-1324`). Il reste `null` dans deux cas :

- tant que la réponse n'est pas arrivée ;
- si le serveur répond `success:false`, ce qui se fait sans aucun message.

Le bouton reste pourtant actif. `onSave` lit `wind.getData().lgPREENREGISTREMENTID` sans contrôle. L'identifiant est
pourtant déjà connu par la configuration `venteId`, posée par `VenteFinisCtr.js:132` et
`FactureSubrogatoireBisManager.js:497`.

**Correctif fait (26/11, avec l'accord de l'utilisateur)**, branche `PRES-/journaux-support-j26-1`, partie de
`plan/24112026` :

- « Enregistrer » est grisé à l'ouverture. Il devient actif dès que la vente est reçue, avant le remplissage, pour
  garder le comportement d'avant si ce remplissage échoue.
- Si la vente n'a pas pu être lue (`success:false`, réponse illisible, échec réseau), le bouton reste grisé et affiche
  « Vente non chargée », avec une info-bulle qui explique quoi faire. Aucune fenêtre ne s'ouvre.
- `onSave` ne fait rien tant que la vente n'est pas chargée.

**Test** : `src/test/e2e/journal/test-enregistrer-tp-avant-chargement.js`, un test d'écran joué sur domain3.

Parcours :

- SERVICE CLIENT > Vente terminées ;
- recherche de la vente, puis clic sur « Modifier info client » ;
- 1ᵉʳ cas : chargement ralenti de 4 s, puis clic sur « Enregistrer » ;
- 2ᵉ cas : chargement refusé (`success:false`), puis clic sur « Enregistrer ».

Le test ne laisse aucune trace :

- tout enregistrement est intercepté et compté (0 attendu) ;
- le droit d'essai est retiré à la fin.

Sur l'ancien code, 4 contrôles sur 9 échouent avec l'erreur du journal (« Cannot read properties of null (reading
'lgPREENREGISTREMENTID') ») : le défaut est **confirmé**. Sur le nouveau code (WAR déployé sur domain3), les 9
contrôles passent.

Non-régression, tests du même écran joués l'un après l'autre :

- `test-infos-client-vente-avant-chargement.js` : 7/7 ;

### J26-2 — Mémoire de CAISSE5

Le Payara de CAISSE5 est limité à 512 Mo et l'auto-diagnostic le signale (MEMOIRE_MAX). C'est un réglage du poste,
pas du code : passer `1-configurer-payara.ps1` sur CAISSE5 pour remonter `-Xmx` au minimum attendu, puis redémarrer le
service. Aucun correctif de code.

### J26-3 — Un poste avec un WAR ancien

Le message de la ligne 23 n'existe plus dans le code depuis le 14/10. Un Payara branché sur cette base exécute donc une
version d'avant le 14/10. Il le fait en mode serveur, puisque le moniteur de jobs ne tourne qu'en mode serveur. Deux
indices le confirment :

- la colonne Version est vide ;
- le fichier de détail est introuvable sur le poste qui exporte.

À vérifier : sur chaque poste, la version affichée dans Centre de support > Stabilité du serveur. Sur le poste local,
il faut aussi vérifier l'ancienne application JSP, qui est branchée sur `capitale`.

Correctif proposé : un poste dont la version diffère de celle du serveur est signalé par l'auto-diagnostic, et ses
événements portent toujours le nom du poste.

### J26-4 — Pool et configuration des postes

Les cinq postes ont un pool sans vérification des connexions. Il faut passer `1-configurer-payara.ps1 -PoolSeulement`
sur chacun.

Sur PARA, il faut lire le détail du contrôle CONFIG_POSTE dans le Centre de support :

- si PARA est en `application.mode=server` alors que la base est ailleurs, le passer en `client` ;
- sinon, mettre le même mode dans ses deux fichiers.

C'est un réglage, sans correctif de code. Le second point est à faire **en premier** si les tâches de nuit tournent en
double.

### J26-5 — SMS d'administration trop long

`sendSMS` envoie le texte tel quel. Au-delà de 700 caractères, Orange refuse l'envoi. Avec plusieurs caissiers, le
récapitulatif du ticket Z dépasse 700 caractères.

Correctif proposé : découper le texte en plusieurs SMS de 700 caractères au plus, aux fins de section (une section
par caissier, puis le total général).

Test de cohérence proposé :

- entrée : récapitulatifs de 1 à 20 caissiers tirés au hasard, avec une graine fixe ;
- règles vérifiées : chaque morceau fait 700 caractères au plus, la concaténation redonne le texte, aucune ligne n'est
  coupée.
